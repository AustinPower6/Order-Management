User documentation — all features, internal relationships and workflows explained.

Start & Navigation

The application opens with a start page and a sidebar on the left. Use the sidebar to quickly reach all functions.

Clicking a button in the sidebar or menu opens the corresponding module as a tab on the right. Several tabs can be open at the same time.

  • Close a tab: click the X on the tab
  • Close a tab (alternative): double-click the tab

The main window automatically saves its position and size. On the next start it is restored at the same location.

Active company at start-up

The program starts with the company you last worked in. The active company is remembered per user — on a shared machine everyone therefore continues where they left off.

If the last active company no longer exists — because someone else deleted it, for instance — the program automatically switches to the first company and reports: “The last active company no longer exists or has been deleted. The company “…” has been activated.” In that case, check whether you really want to work in the company shown.

Focus Highlighting

The input field that currently holds the cursor and expects input is displayed inverted — foreground and background colours are swapped. This makes it obvious at a glance where input is expected. Read-only display fields are not highlighted.

Sidebar & Document Date

The sidebar on the left shows the current document date below the user name. This date is used as the default value for new documents (quote, order, delivery note, invoice, reminder).

Setting an override date

By default the document date matches today's date. However, you can set an arbitrary override date:

  • Left-click on the date opens a calendar dialog where you can pick any date.
  • Right-click on the date shows a context menu:
    • Set to today's date — resets the document date to today.
    • Remove override date — removes the manually set date; today's date is used again from now on.

The override date is not persistent — on application restart it is automatically reset to today's date. This prevents mistakes from working with yesterday's date the next day.

Practical tip: The override date is useful when you need to create a document retroactively (e.g. an invoice on March 5 for a delivery from February 28).

Master Data — Overview

Master data is the foundation of every document. Without correct master data, neither PDF printouts nor document chains work correctly.

The three master data modules are interconnected:

  • Company — your business: address, bank details, VAT classes, conditions, standard texts, markers
  • Customers — recipients of all documents; every document references a customer
  • Articles — products and services; every line item on a document references an article

Company

The company master is the central configuration module. It contains all master data of your business as well as every setting that controls the behaviour of the whole application. The dialog is split into several tabs.

Address & Contact

Contains all contact data of your business that appears in the letterhead of every PDF printout:

  • Company number — three-digit identifier of the company (read-only). If the company is soft-deleted and the admin switch “Show deleted companies” is active, the suffix “(deleted)” appears after the company number. The internal record ID can appear right after it — but only if the admin switch “Show record ID” is active.
  • Company name, short name, additional line — appear in the header of every document
  • Street, house number, house number suffix, ZIP, city — sender address in the PDF letterhead and as the sender line above the address window. House number and suffix are separate fields; they are required e.g. for the ELMA XML of the EC Sales List.
  • Phone, fax, email, website — appear on the right of the letterhead
  • IBAN, BIC, bank name — in the footer and on reminders as the payment target. Next to the IBAN there is the button “Determine BIC/bank”: it checks the IBAN entered and fills BIC and bank name from it — for German IBANs offline from the bank-code registry (GDPR-compliant, no internet lookup). When you leave the IBAN field, BIC/bank are filled automatically only if they are still empty; the button, by contrast, overwrites existing values. An invalid IBAN is shown as a notice. Note: resolving foreign IBANs is not active yet.
  • Currency, country code — control the currency symbol (€, CHF …) on all documents
  • Company language — selected from the languages table (tab Parameters → Languages). It determines the language in which units and print texts are displayed in the application and is the starting point of the AI translation at print time. New companies default to “German”; the field may also stay empty, in which case no translation takes place. Details see Translation at Print Time.
Tax data moved: Tax number and VAT ID are no longer maintained here but in the dedicated tab Taxes.

Taxes

The “Taxes” tab bundles the tax-related master data and the details for electronic reporting to the German Federal Central Tax Office (BZSt):

  • Tax number and VAT ID — appear in the footer of every invoice and reminder. The VAT ID is also a prerequisite for intra-Community supplies (print, e-invoice, EC Sales List).
  • ELMA account ID — your BZSt account ID; mandatory for exporting the EC Sales List as ELMA XML.
  • ELMA environment — Production or Test; controls which BZSt environment the generated ELMA XML is addressed to.

Email & E-Invoice

The “Email” tab configures e-invoicing and email dispatch:

  • Create e-invoice: Activates automatic generation of machine-readable XML files on the first print of an invoice (EN 16931).
  • E-invoice format: Default format for all customers without a customer-specific setting (UBL 2.1, UN/CEFACT CII, XRechnung 3.0, ZUGFeRD).
  • Email client: Sets which service is used to send emails (Brevo API, Gmail SMTP, Outlook 365 Classic, New Outlook, SMTP). Depending on the choice, additional fields appear. Details see Email Outbox.
  • Email dispatch default per document type: preset for whether an outbox entry is created automatically on printing (0 = none, 1 = PDF only, 2 = XML only, 3 = PDF + XML).
  • Email signature & privacy policy: Appended automatically to the email text.

Parameters

The “Parameters” tab bundles five company-specific master data tables as sub-tabs:

  • Product groups — categorisation of articles (e.g. “Services”, “Hardware”). Available for selection in the article master. Add, rename, delete.
  • Units — quantity units (pcs., h, kg, m² …) per company, with a translation per language. Add, edit, delete; deleting is blocked while articles use the unit; renaming affects all affected articles. Newly created companies automatically receive a set of default units; every company should have units defined, since line items pick their unit from this list. Details see Print Texts & Units per Language.
  • Brands — manufacturer brands per company, each with a logo. Add, edit, delete; deleting is blocked while articles use the brand; renaming also renames the logo file. The logo is stored by convention ({brand logo directory}\{company no.}\{brand}.png).
  • Languages — all languages in use, with AI support and fallback. Details see Languages & Country Codes.
  • Country codes — ISO code, country and main language; used for the country selection in the company and customer master. Details see Languages & Country Codes.
Note: Units and brands used to be maintained directly in the article master — they now live centrally here in the company master. In the article master they are only selected.

Accounting Link

Configures the accounting export for your financial accounting software:

  • Output format — company-wide choice of the export format: JSON (default), DATEV format (EXTF booking batch, CSV) or DATEV Rechnungsdatenservice (documents, ZIP). Details see Booking Export.
  • DATEV consultant no. and DATEV client no. — only with one of the two DATEV formats; both are then mandatory. If missing, the booking export blocks with a hint.
  • Select the chart of accounts (e.g. SKR03, SKR04) for the active fiscal year
  • Define number ranges for general ledger and debtor accounts (from/to)
  • VAT accounts table: assign a revenue and VAT account per VAT class; the … button opens the account search in the selected chart of accounts. On export, the revenue account is matched via the (fixed) tax key of the class — renaming a VAT class later is therefore harmless.
  • Reminder fee account and reminder interest account for the tax-free reminder line items
  • Tax class for reminders — VAT class used for reminder line items (must be configured, otherwise the export blocks the reminder document, see Reminders)
DATEV tax key: If a DATEV format is selected, the tab VAT management additionally shows a field “DATEV tax key” per VAT class (BU key). Every class in use — including tax-free ones — needs a value there, otherwise the DATEV export blocks with a hint. With JSON the field is hidden.

Details on the export process see Booking Export.

Layout

Controls the visual appearance of all PDF printouts: font family and font size for the header, line items and footer, plus the height of the shipping address block (“space until subject”). Changes take effect immediately on newly generated PDFs; existing printouts remain unchanged. New companies are pre-filled with sensible defaults (e.g. shipping address height 55 mm), which can be changed at any time.

Control

Bundles switches that control the printing behaviour:

  • Print article number — if the checkbox is ticked, the column header of the description column reads “Article number: Description” and every line item is printed as “{article number}: {description}”. The printed number comes from the line item snapshot (see Line Items); manually entered line items without an article master record have no number. You can adapt the header text in the Print Texts tab.
  • Print description / safety information / manufacturer information — three switches that set company-wide whether the respective article texts are printed on the line item row. This default can be overridden per article and text field (three-state switch in the article master: inherit from company / always / never). Safety and manufacturer info are pulled live from the article master at print time.
  • Disclaimer for translated customer copy — editable notice text printed in the footer of the translated customer copy (red, regular font). Placeholders: {firmensprache}, {kundensprache} and {LLM} (= translation model used). If the field is left empty, the default text is used automatically when printing — the AI labelling required by the EU AI Act cannot be omitted. See Translation at Print Time.
  • Retention period (years) — tax/commercial retention period (default 10), decisive for the GDPR anonymisation. As long as it is running for a customer's documents, deletion is blocked. See Data Protection (GDPR).

The Control tab also holds the setting “Check document archive (years)” (0 = off; controls the background integrity check of the document archive), the actions for the digital PDF signature (create/import certificate, activate signing) as well as a status row “Key file (API keys)”:

  • It shows whether the company's encrypted key file is present, missing or corrupt. This file holds all secret credentials (API keys, SMTP/app/certificate passwords) encrypted outside the database — see Database & Backup.
  • Reset: if the file is corrupt or you want to start over, delete it (app\daten\api_keys_{company number}.json) — a new key password is assigned automatically on the next save; you then re-enter the actual keys/passwords in the respective tab (AI connection, email, address verification).

Address Verification

The “Address Verification” sub-tab (Company master → Parameters) configures the verification of customer addresses via the “Verify address” button in the customer master. Only the address is checked (street, additional line, ZIP, city, country) — name and company name are never transmitted to the service (data minimisation, Art. 5 GDPR).

  • Provider — choice of verification service:
    • Nominatim / OpenStreetMap (self-hosted) — the privacy-friendly default: requests go exclusively to your own self-hosted Nominatim instance, no data is transferred to third parties. Deliberately conservative — at best, Nominatim returns a suggestion for confirmation, never an automatic confirmation.
    • Google Address Validation (external) — external US service with component-level verification (can also confirm addresses automatically). Only usable after a GDPR attestation (see below).
  • Nominatim base URL — address of your own Nominatim instance (e.g. http://localhost:8080).
  • Google API key — visible and editable for admins only; other users see a masked display (********) and the stored value is preserved on save.

GDPR attestation (privacy by default): Google only becomes usable once an admin documents via the “Record attestation…” button that the data processing agreement (DPA) with Google has been concluded and the record of processing activities (ROPA) has been updated. Every attestation is permanently logged with user and timestamp; it can be revoked at any time (uncheck the boxes and click OK) — the revocation is appended as a new entry and earlier entries remain traceable (accountability, Art. 5(2) GDPR). Without a valid attestation Google is locked: verification then runs automatically via Nominatim, even if Google is selected as provider and an API key is stored. The status label on the tab shows the current state.

Important: The attestation documents the operator's decision — it does not replace a legal review; the controller within the meaning of the GDPR remains liable. See also Data Protection (GDPR).

Print Texts

The tab shows all labels of the PDF documents that can be captioned — divided into standard document texts (fixed) and condition labels (dynamic per company):

  • Standard document texts (document info, line-item table, summary, footer, reminder, journal columns/names) are read-only here and only show the translation currently in force per language (from the app language file, keys druck.*). They are changed centrally in the language generator via the “Print texts only” view — this way the same document texts apply consistently across all app languages.
  • Condition labels (VAT classes, payment terms, reminder levels) remain editable and translatable per language here — they depend on the company and its master data and do not belong in the app language file.

A language dropdown at the top of the tab lets you choose the language to display or — for conditions — to maintain. When printing for a customer with a different language, the labels are taken from the matching language set. A note at the top explains the split. Details see Print Texts & Units per Language.

AI Connection

Activates and configures the company's AI connection (OpenRouter, Anthropic or a local, OpenAI-compatible model). Basis for the AI spell check in the article master and the translation at print time. Described in detail under Setting up the AI Connection.

Signatures

Per document type (quote, order, delivery note, invoice and reminder) there are two fields printed as the two columns of the signature block in the PDF: “Place, date” (left) and “Signature” (right, e.g. name and role of the signer). Both are printed as entered (no auto-translation); if both are empty, no block is printed. For new companies the right field is pre-filled with “Signatures”.

Note: The former automatic “place, date” print text (Print Texts tab) is gone — enter place/date directly into the left field now.

Greeting phrases: Two company-wide greeting phrases inserted into documents and email texts via markers: polite (marker {Gruß 😄}, default “Mit freundlichen Grüßen”) and dispute (marker {Gruß 😠}, default “Hochachtungsvoll”). The standard and email texts of new companies end with {Gruß 😄}.

Standard Texts

Text snippets for quotes, orders, invoices, delivery notes and reminders — including the staged reminder texts (Payment reminder, 1st reminder, 2nd reminder, Final notice). You can use markers that are replaced automatically when printing. Details see Standard Texts & Markers.

Email Texts

Pre-filled subject and body templates for automatic email dispatch — one per document type and reminder level. Marker buttons allow quick insertion of placeholders (document number, amount, due date etc.).

Salutation: The personal salutation is no longer prepended automatically. Instead, the marker {Anrede} (resolves the customer's letter salutation) is placed at the start of the email template.

Copies

Number of copies per document type (e.g. duplicate invoices).

Paths

Path definitions for all generated and loaded files:

  • Export path: base directory for all generated files (PDFs, XMLs, emails). Empty = program directory. The Browse button opens a folder selection dialog.
  • Logo path: path to the company logo image (PNG/JPG) shown in the letterhead. A live preview shows the image directly.
  • Article directory: base directory for product images. Images are stored by convention per company ({article directory}\{company no.}\{article number}.jpg) — no path per article.
  • Brand logo directory: base directory for the brand logos ({brand logo directory}\{company no.}\{brand}.png).
  • Directory for GDPR exports: storage location of the access reports and batch-run logs. Empty = {export path}\DSGVO\. See Data Protection → Storage & Logs.
  • Relative subfolders for printouts, booking export, e-invoice, email attachment — the resolved absolute paths are shown as a hint.

Verify Address

The “Verify address” button sits on the country row. It verifies the entered address (street, additional line, ZIP, city, country) via the service configured in the company master (see Company master → Parameters → Address Verification) — name and company name are not transmitted. The result appears as a hint line below the country field:

ResultMeaning / behaviour
Address confirmedThe address was fully confirmed — no further action needed. (Only possible with Google; Nominatim returns at most a suggestion for confirmation.)
Standardized suggestionThe service suggests a standardized spelling. A dialog compares the entered and the suggested address: Yes applies the suggested values to the fields (non-empty values only; save as usual afterwards), No leaves everything unchanged.
Rejection (red)The address is incomplete or contains suspicious components, no match was found, or the service is unreachable — check or correct the address manually.
Note: Verification runs on demand only — saving the customer never triggers an automatic call. If no verification service is set up yet, clicking the button shows a message pointing to Company master → Parameters → Address Verification.

AI Spell Check

Below the fields Long description and Safety information there is a button “Spell check” each. It is only active when the company's AI connection is set up. A click sends the field content to the model. The application evaluates the answer and reports back clearly:

  • If the text is free of errors, the message “The AI found no errors.” appears — no correction dialog opens.
  • If the text could not be checked, “The text could not be checked.” appears.
  • Only for real corrections does the comparison dialog open, with the original (top, read-only) and the correction (bottom, still editable) — without technical markers in the text. Only Save applies the correction to the field; Cancel discards it.

Customer Information System

Customer Info brings together everything known about a customer on one page: master data, revenue, every document and the complete history of your correspondence. From here you place calls, write emails and letters — and each of those actions is recorded in the history automatically.

Open it from the sidebar → Customer Info, or from the customer master using the Customer Info button — the selected customer is then already chosen. Customer Info is a separate part of the program in the permission matrix; without read permission it does not appear at all.

You pick the customer at the very top. That field is a search box: type part of the name or customer number instead of scrolling the list. Four areas follow below.

AI Connection & Multilingual Printing

The application can connect an AI language model (LLM) for two tasks: the spell check of article texts and the translation of documents into the customer's language. Both are optional — without an AI connection the application keeps working unchanged, just monolingual.

Overview: You configure the model once in the company master (tab AI Connection), maintain your languages and country codes, pre-translate the fixed print texts and units per language — and when printing for a foreign-language customer the AI translates the dynamic content automatically.

Translation at Print Time

As soon as the company language (company master → Address) and the customer language (customer master) are set and different, the AI translates the dynamic content into the customer language when printing:

  • Subject and free texts (text above / text below)

Creating Additional App Languages

In addition to German and English you can generate further user-interface languages of the application yourself. Open the generator via the hamburger menu (admin) with the red entry “Create/update app language …”. The UI texts are translated by the AI of the active company, automatically back-translated and rated, and written to a separate file per language. The finished language appears immediately in the language selection of the sidebar.

Prerequisite: The AI connection of the active company must be set up and active. For reliable results we recommend the LLM of an established provider (see model recommendation above). Which models execute the three tasks translation, back-translation and rating is controlled by the LLM assignment.

How Everything Fits Together (Block Diagram)

The base language file language.json contains every UI text in German and English, together with a timestamp and content hash per text. The generator reads the source texts from it, has the AI translate and check them, and writes the result to two files per language: language.<code>.json (the translations) and language.<code>.review.json (back-translation, confirmation status and the source-text stamp at translation time). The app UI loads the additional languages from these files; the list of installed languages (installed_languages.txt) additionally feeds the dictionary installer for spell checking.

Choosing Target Language and Source

Target language. The “Language” selector first lists the existing additional languages, then suggestions from the country codes of the company master (“➕ {language} ({ISO})” — code = ISO code, name = the language assigned to the country), the entry “All languages (bulk update)” (see below) and finally “New language …” for free input (e.g. regional codes). Language proficiency check. The result appears behind the displayed AI model (“Proficiency: …”); if a different LLM 2 performs the back-translation, both grades are checked. If a grade is worse than 6, the translation is rejected: the run buttons are locked and a click explains the rejection.

Control Fields and Buttons

  • Batch size (default 20, range 5–50): forward and back-translation run in packages of this size instead of text by text (one AI call per package, prompt “bulk/batch translation”). Smaller size = more robust, larger = fewer calls. If the AI swallows texts in a package, it is automatically repeated and, if necessary, caught up text by text — invisible to you.
  • “Re-translate all texts”: translates all texts again, not only the open ones.
  • Create/update: starts the complete run (see flow chart below) over all open texts — missing, changed (outdated) and not yet confirmed ones.
  • “Translate missing only”: restricts the run to texts without a translation (leaves open red rows untouched).
  • “Check semantic match”: runs only the rating phase (phase 3) for the open red rows.
  • “Poor – retranslate” / “Good – retranslate”: specifically retranslate all rows with the respective rating — taking the rating into account, up to 3 attempts per row, the best result is kept (target “very good”).
  • “Show all”: shows all already translated entries of the language for review (including confirmed and consistent ones) — without AI calls.
  • “Print texts only”: shows exclusively the document print texts (druck.*) — including the print-text defaults that are otherwise hidden — so that they can be translated into all app languages. This is how you maintain the standard document texts shown read-only under Company → Print Texts centrally. The row counter reflects the reduced scope; the option works together with “Show all”.
  • “Cancel”: stops the run immediately — even in the middle of a running AI call, without waiting for its answer. Finished rows are kept (the intermediate state is saved continuously anyway).

The Translation Run (Flow Chart)

The run works batch by batch: each batch passes through the three phases completely before the next one starts. After each phase or checked row the state is saved — if the run stops (cancel, error, crash), all finished parts are kept and are available immediately the next time you open the dialog.

Flow chart: the three phases of the batch run with translation, back-translation and rating/correction

About phase 3: each row gets exactly one back-translation (to detect a discrepancy). If it deviates, the rating call runs (prompt “match check & correction”): in a fixed four-line form it returns one of the four accuracy grades — identical, very good, good, poor — and, for a less-than-perfect translation, an improved version right away (@@KORREKTUR). If the check returns a correction, it is applied automatically and the row counts as confirmed (green) — without another control back-translation (this saves AI calls). The back-translation column still shows the back-translation that triggered the discrepancy (the rating star with grade/reason serves as evidence). Without a correction the grade decides (“identical”/“very good” = done, “good”/“poor” = stays open for rework). The source text is no longer checked — it is considered authoritative.

The former “passes” setting is gone: there is only one continuous batch run. Rework remaining rows specifically — via “Translate missing only”, “Check semantic match” or the retranslate buttons.

Control Table and Color Legend

A continuously filled table shows the run live with the columns No. · key · original · translation · back-translation · confirmed · action. The display matches the color legend below the table:

  • Red text: translation is missing, outdated or the back-translation deviates from the original (open).
  • Green text: rated identical by the AI (perfect rendition).
  • Normal font: consistent — the back-translation matches the original (confirmed or without objection); a row rated very good is also shown normally (black).
  • Light-gray original cell: the German/English source text was changed after the translation — the row is outdated and will be re-translated on the next run.
  • Bold italic: the AI changed the translation during the current operation (match check/correction) — purely visual for the current view.
  • Italic (original and back-translation column): the back-translation deviates from the original — both columns are shown in italics (italic only; bold italic stays reserved for the AI change), including for rows confirmed in green.
  • Red background inside the translation text: broken {…} placeholder. Format placeholders such as {n} must be taken over unchanged; the tooltip names wrong/extra and missing placeholders. Such rows count as open/incomplete and are re-translated on the next run — preventing texts that would break at runtime.
  • Colored star behind the confirmed checkbox: the AI rating — ★ green = very good/identical, ★ yellow = good, ★ red = poor. The mouse tooltip shows the AI's reasoning.

Non-European scripts (e.g. Khmer) that Windows does not cover are displayed correctly — the required fonts (Google Noto, OFL license) live under app/fonts/ and are loaded automatically when needed.

Row Actions

  • Confirmed checkbox: a red row (literally deviating but semantically correct) can be confirmed manually — it then counts as done.
  • Double-click on “translation”: opens an edit window (with spell checking in the target language). After the change the row is automatically marked as confirmed.
  • “Retranslate” (action column): translates the row completely anew — forward, backward, and on deviation a rating with automatic correction take-over. If the rating reports a grammar error in the source text, the confirmation workflow applies (see below); after approval the whole procedure starts over once.
  • “Rating” (action column): shows grade (with traffic-light star) and reasoning of the last AI rating — also for consistent rows without a star tooltip.

Translation log per language

  • The complete batch calls (several rows per AI call) are additionally listed under batch_calls with the keys involved.
  • The log is collected per app session and language and sits next to the language file (not under version control).

Workflow & Document Chain

The typical workflow runs in stages. Not every stage is mandatory: you can go directly from quote to order, and from order to invoice (skipping the delivery note), and the reminder process is only triggered on unpaid invoices.

Document flow: mandatory chain and optional paths. Status changes appear on the respective document.

Document Chain in Detail

Every document is linked to its predecessors and successors. This linking is called the document chain. The link is established through foreign keys (IDs) on the successor document that point to the predecessor.

Document chain: each successor stores the ID of its predecessor. Bidirectional navigation starts from any document in the chain.

In detail:

  • Quote → Order: The order stores the angebot_id. The system thus knows from which quote the order originated.
  • Order → Delivery Note: The delivery note stores the auftrag_id.
  • Order → Invoice (direct): For pure services the delivery note can be skipped. The invoice stores only the auftrag_id.
  • Delivery Note → Invoice: The invoice stores the lieferschein_id and (if present) the auftrag_id of the source order of the delivery note.
  • Invoice → Reminder: Every reminder stores the rechnung_id and the mahnstufe (level).
  • Reminder → next level: Higher-level reminders point to the previous reminder.
Document chain in the dialog: When you open a document, you see the entire chain at the top — from the first quote to the last reminder. Deleted documents are shown with a marker so the chain remains traceable even after deletions.

Backward and forward through the chain

The document chain is bidirectional:

  • Backward: From the current document to the first predecessor (usually the quote). This always shows which quote an invoice is based on.
  • Forward: From the current document to the last successor (e.g. from the invoice to the highest reminder level). This shows how overdue a payment is.

Delete protection through the chain

When you try to delete a document that has live successors, deletion is prevented. The system shows a warning with the list of blocking documents.

Example: You cannot delete a quote if an order has already been created from it. You cannot delete an order if an invoice already exists.

Caution: This only applies to live (not deleted) successors. If the order has already been deleted, you can delete the quote.

Delete & Restore

Documents are never actually deleted, but marked as deleted (soft delete). This has the following effects:

  • Deleted documents do not appear in the normal lists.
  • Deleted documents appear in the document chain with a marker (e.g. struck-through or grey).
  • Deleted documents can be restored — they reappear in the list.
  • The number of a restored invoice is not reassigned (it keeps its original number).

Preventing deletion (delete protection)

The system checks for live successors before every deletion:

Document typeDeletion blocked by

How the counter works

The counter is kept for all five document types — including reminders.

When two users save at the same time

If two workstations assign the same number at the same moment, the program automatically moves on to the next free one — you will not notice a thing. VAT System

The VAT system works with classes and time-dependent rates.

Classes

Every VAT class (e.g. “Standard rate”, “Reduced rate”, “Tax-free”) has multiple rates with a start date. Example:

ClassRateFrom date
Standard rate15 %01.01.2024
Standard rate16 %01.07.2024
Standard rate18 %01.01.2025
Reduced rate7 %01.01.2024

Fields of a VAT Class

When creating/editing a class you define:

  • Name and (with the first rate) rate % plus valid from.
  • Tax key (1–99): passed unchanged into the booking export; the accounting software calculates the VAT from it. It is fixed — selectable only when a class is newly created, locked afterwards; another rate of the same class inherits it automatically. Background: the booking export matches the revenue account via this immutable key (not via the renamable name), so documents stay bookable even after the class is renamed.
  • DATEV tax key (BU key): only visible when a DATEV output format is selected in the Accounting Link tab. It is used as the BU key on DATEV export; every class in use (including tax-free ones) needs a value, otherwise the DATEV export blocks. With JSON format the field is hidden.
  • Note text (print): appears on the document below the totals (e.g. a tax exemption note). On the translated customer copy it is translated as well.
  • Intra-Community supply (flag): marks the class as intra-Community supply — enables the igL document switch and the prerequisite check when printing invoices. See chapter Intra-Community Supply.

Freezing the VAT rate

When you create a line item on a document, the rate valid at the document date is stored in the line item. The rate is thus frozen — later changes to the VAT class do not affect the document anymore.

When a line item is created, the system reads the rate valid at the document date from the VAT class and stores it permanently in the line item. Later changes to the class do not affect the document.

Example sequence:

  • Document of 2025-03-15 with standard rate → line item gets 18 %
  • Rate increase to 20 % effective 2025-06-01
  • Document of 2025-06-10 with standard rate → line item gets 20 %
  • The old document of 2025-03-15 stays at 18 %
Why this matters: When you reprint old documents, they show the correct VAT rate for the time of creation. Nothing needs to be adjusted manually.

How reminders work

The reminder process is staged. Levels are assigned automatically (1 to 4):

LevelDescription
1Payment reminder

Each level has:

  • A due period in days (e.g. 7, 14, 30 days)

Finalisation & Frozen Values

On the first original print a document is finalised (the creation date is set; after that it can no longer be edited). From that moment on, the values printed on the document are unchangeable — later changes to master data or conditions only take effect in the follow-up document (document consistency). Besides the customer and the line items (VAT rate, unit, article number, description), the following are frozen as well:

  • the payment condition (due date, “payable within days”, label) and the VAT class tax note;
  • per line item the safety notes and the manufacturer information;
  • for reminders additionally the header values interest rate, due date, payable-within-days and reminder-level label — a later change to the base interest rate or the reminder condition therefore no longer affects reminders that have already been printed.
Existing documents: Documents finalised before this freeze logic was introduced freeze these values on their next printout (from the data current at that time).
A failed first print stays a draft: The document is finalised only after the PDF has been created successfully. If printing fails (e.g. a path or file error), the document remains a draft and editable, and the next print is again a regular first print (including the e-invoice).

Digital Signature of Document PDFs

On request the program digitally signs every document PDF sent to customers at print time (PAdES/PKCS #7). The signature “seals” the content: if the PDF is later changed by so much as a single character, signature validation fails in the PDF reader. Subsequent tampering is therefore detectable.

Activating

  1. Company → Parameters → tab Control: click Create certificate once. The program creates a self-signed company certificate; its password is assigned automatically and is never shown.
  2. Then tick Sign PDF documents digitally and save.

The certificate is stored as a .p12 file under {signature directory}\{company no.}\zertifikat.p12 (Company → Paths → Directory for signature certificates; empty = {export path}\Signatur-Zertifikate\). Signing happens on every real print — never on test prints (watermark). The copy sent by email is signed as well.

As visible evidence, a signature stamp appears at the bottom left of the last page (“Digitally signed”, company name from the certificate, date and time). The actual validation still takes place via the signature field in the PDF reader.

Self-signed = yellow warning triangle: At the recipient the PDF reader initially shows “Signature is valid, but the signer's identity could not be verified” (yellow triangle). That is normal for a self-created certificate. The protection against undetected changes still works completely — only the origin is not yet confirmed.

Trusted certificate (green check mark)

A certificate is not “created trusted” — trust is established afterwards. To get a green check mark instead of the yellow triangle, there are two ways:

Option 1 — the recipient marks your company certificate as trusted, once (free of charge, works with the certificate created above). Ideal with a stable set of customers. In Adobe Acrobat Reader the recipient does the following once:

  1. Open the signed PDF and click the signature bar or the signature field → Signature Properties.
  2. Choose Show Signer's Certificate….
  3. Tab Trust → Add to Trusted Certificates….
  4. Tick the option “Use this certificate as a trusted root” and confirm with OK.
  5. Validate the signature again (close/reopen the reader if necessary) — the green check mark now appears.
Security note: The certificate is already contained in the signed PDF — it does not have to be sent separately. Before marking it as trusted, the recipient should compare the certificate's fingerprint (SHA-256) with you over a second channel (telephone, known letterhead), so that the trust is genuinely justified. The setting applies per recipient and per program.

Option 2 — a certificate from a trust service provider (paid, universal). A certificate obtained from a recognised provider is trusted without any action by the recipient. For the automatic green check mark in Adobe, the provider must be listed in the Adobe Approved Trust List (AATL) or the EU Trusted List (EUTL). Providers include D-Trust (Bundesdruckerei), GlobalSign, DigiCert, Sectigo and SwissSign. Depending on the certificate class (advanced/qualified) there are annual costs and an identity check may be required.

Adding it to the program: A purchased certificate comes as a .p12 or .pfx file with its own password. Add it via Company → Parameters → Control → Import certificate: choose the file, enter the password. The program then signs with this trusted certificate; the status shows “(imported / trusted)”. The Create certificate button, by contrast, always creates a self-signed one — “(self-signed)”. After creating or importing, the program asks whether signing should be activated right away.

Checklist for buying a certificate

So that a purchased certificate works directly via Import certificate, watch out for these points at the provider:

  • File format PKCS #12 (.p12 or .pfx) including the private key. A plain .cer/.crt file contains only the public part and cannot sign — the import rejects it.
  • Software certificate (also called “soft PSE” / exportable as a file). Hardware-bound certificates on a smartcard, USB token or in an HSM cannot be imported as a file and do not work with this program. (Qualified signatures under eIDAS are frequently hardware-bound — unsuitable here.)
  • Intended use: document/PDF signing (“Document Signing”). Not suitable: pure email certificates (S/MIME) or web server certificates (SSL/TLS).
  • For the green check mark in Adobe: the issuer must be listed in the AATL (Adobe Approved Trust List) or the EUTL (EU Trusted List). Providers include D-Trust, GlobalSign, DigiCert, SwissSign and Sectigo.
  • Have the password ready: the password assigned to the .p12 file at purchase or export is requested during the import.
  • Validity is usually 1–3 years. After expiry you import a new certificate — documents already signed remain verifiable with the old one.

The import checks the file: if the private key is missing or the password is wrong, an error message appears and nothing is taken over.

Long-term archiving: For verifiability far beyond the certificate's expiry date, a qualified time stamp (RFC 3161) would make sense. A time-stamping service is currently not integrated; for day-to-day operation (tamper detection at the recipient) it is not required.

When signing is not possible

If the certificate is missing or the required components are not installed, the PDF is delivered unsigned and the case is recorded in the error tracking — printing does not abort.

Locking System

When several people work with the program at the same time, the locking system prevents two users from changing the same record and overwriting each other.

How it works

Locking happens per record — not for a whole module. Whoever clicks Edit (or double-clicks) takes the record; everyone else can only view it in the meantime:

  • If the record is already being worked on, the message “The record is being edited in module … by user …” appears and the dialog does not open.
  • If two users click Edit at the same time, exactly one gets the record — the other reliably receives the message.
  • The lock ends as soon as you save or close the dialog.
  • When merely viewing (rights level read) no lock is set — whoever only reads blocks nobody.

The company master: a question instead of a lock

The company master is not locked while being edited — its tabs often stay open for a long time, and nobody should be locked out by that. Instead the program checks on saving whether another user has saved the company master in the meantime. If so, the following question appears:

“The record was changed on … by user … in module …. Your entries would overwrite that change. Save anyway?”

  • No aborts the save — your entries stay in the form. With Cancel you can discard them and reload the current state.
  • Yes saves and overwrites the other change.
  • Your own changes from another tab do not trigger the question.

Locks overview (Company → Locks)

The overview shows all active locks. It is reserved for administrators — only they can release a lock.

Releasing stuck locks

If a machine crashes while a record is being edited, the lock stays in place. An administrator releases it in the overview — check beforehand, using User and Locked since, that nobody is really working on it any more.

If releasing a lock fails when a dialog is closed, the case is recorded in the error tracking (module “Multi-user lock”) and can be released here.

Caution: If you release a lock while someone is genuinely editing the record, their changes may be lost. When in doubt, ask them first.

Booking Export

The booking export hands finalized documents of a booking period over to accounting. The output format is chosen company-wide in the Accounting Link tab; depending on the choice, a JSON file, a DATEV EXTF booking batch (CSV) or a DATEV Rechnungsdatenservice package (ZIP) is produced — each in addition to the print list (PDF, landscape). Open the window via Booking export in the sidebar.

Overview of Not-Yet-Exported Documents

Above the export table sits a framed month table: one row per year (in which not-yet-exported booking-relevant documents exist) with 12 month columns and the number of open documents per month. If all documents are exported, the hint “All documents are exported.” appears instead. The table refreshes automatically (after new exports, cancellations, refresh). It shows all open periods across all years — in contrast to the hint list in the “New export” dialog, which only covers the selected year.

Prerequisites (one-time setup)

  • Company → Number ranges: per VAT class set the revenue and output-VAT account as well as the reminder-fee and default-interest account; optionally the receivables account (collective account, reference only). The debtor (debit side) is the customer number (personal account). On every account field the … button opens the account search in the configured chart of accounts.
  • Company → Paths: set the booking export directory.

Which documents are exported

  • Finalized invoices (including cancellation invoices) of the selected period.
  • Reminders with reminder fee and/or default interest (tax-free) — only the amounts of their own reminder level.
  • The booking period is determined by the document date.

Creating a new export

  1. Button New export. The dialog prefills booking year and period from the company settings; a hint list shows how many documents per period are not yet exported.
  2. On confirmation the JSON file (Buchungen.{CompanyNo}.{Year}.{Period}.{Timestamp}.json) and the print list are created.
  3. The included documents are marked with the export number (column “Export” in the invoice/reminder list).

Booking format

One line per booking in account-to-counter-account format with gross amount and tax code (the accounting system derives the VAT from the tax code). The print list shows the debit and credit totals with a zero-balance check (difference must be 0.00).

  • Cancellations: cancellation invoices and cancellation reminders go into the export as negative bookings (DATEV EXTF: debit/credit indicator “H” with a positive turnover; DATEV Rechnungsdatenservice: amount with a minus sign). Cancellation reminders are included in the next export even without a prior printout.
  • Reminders: per reminder only the reminder fee and default interest of its own reminder level are booked (items of earlier levels carried on follow-up reminders were already booked with their own reminder) — the monthly counters in the overview count only such reminders too.
  • Amounts: The booking total of an invoice always matches the printed invoice amount exactly; any cent rounding differences across several VAT groups are balanced out.
  • Concurrency protection: if two users export the same period at the same time, the second export aborts with an error message (no duplicate handover to accounting).

Intra-Community Supply (igL)

An intra-Community supply (German: “innergemeinschaftliche Lieferung”, igL) is a supply of goods from your business to a business in another EU member state. It is VAT-exempt for the supplier (0 %); taxation happens at the recipient (destination principle). This chapter describes the whole process in context — from setup through the invoice and printing to the e-invoice, booking and reporting.

Set up master data → igL invoice (switch) → Print & check → E-invoice (cat. K) → Booking → EC Sales List

Prerequisites of a Tax-Free igL

  • The recipient is a business in another EU member state and uses a VAT ID of that state.
  • Company and customer country are different EU member states (both EU members on the document date).
  • The goods actually arrive in the other member state (documentary evidence, e.g. entry certificate — to be kept outside the program).

Setup (one-time)

  1. Create a VAT class (see VAT System): a class “Intra-Community supply” with rate 0 %, a tax key (the value your accounting/DATEV uses for the tax-free igL), the note text “Tax-free intra-Community supply” and the flag “Intra-Community supply” set.
  2. Revenue account (company master → Accounting Link): per fiscal year, assign this class's revenue account (e.g. SKR03 8125 / SKR04 4125 “Tax-free intra-Community supplies”).
  3. Country codes (Parameters → Languages & Countries): EU membership is stored date-dependently per country (accession/exit). Everything is pre-filled for the EU states — normally no intervention needed.
  4. Customer master: maintain the EU customer's VAT ID and country.
Why the VAT class? “igL” depends on the customer, not the article. You sell the same article domestically at 19 % and to an EU customer at 0 %. That is why igL is not set on the article but switched to the igL class via the document switch (below).

Creating an igL Invoice

In quotes, orders, delivery notes and invoices, next to the customer row, there is the checkbox “Intra-Community supply (tax-free)”:

  • Activating switches all line items to the VAT class flagged as igL (0 %) — including ones added later. Deactivating switches them back.
  • If you pick a customer who qualifies (EU abroad, VAT ID present, different country than the company), the switch is set automatically (with a short notice). You can untick it at any time.
  • The checkbox is only active when exactly one VAT class is flagged as “Intra-Community supply” (otherwise greyed out, with tooltip).

Printing the igL Invoice

  • The customer's VAT ID is printed in the header/meta area as soon as it is stored in the customer master.
  • The mandatory note (note text of the VAT class, e.g. “Tax-free intra-Community supply”) appears below the totals. On the translated customer copy it is translated as well.
Hard prerequisite check: If an invoice uses the igL class, printing/finalizing is blocked when a prerequisite is missing — company or customer country not an EU member on the document date, company country = customer country, or missing customer VAT ID. The error message names the missing condition. The test print does not block.

E-Invoice

For an igL invoice the e-invoice (UBL / XRechnung / CII / ZUGFeRD) automatically sets tax category “K” with the exemption reason VATEX-EU-IC and includes the buyer's VAT ID. You do not need to do anything extra — the prerequisite is complete master data (VAT IDs of company and customer). See also E-Invoice.

Booking

The booking export books an igL line item debtor to igL revenue account with the configured tax key (gross amount = net amount at 0 %). Accounting thereby books it tax-free.

Tip: An igL invoice should contain only igL line items (do not mix in another 0 % class), so print, e-invoice and booking are unambiguously attributed to the igL.

Reporting

Intra-Community supplies must be reported to the German Federal Central Tax Office in the EC Sales List (Zusammenfassende Meldung, ZM) — see the following chapter EC Sales List (ZM).

EC Sales List (ZM)

In the EC Sales List (German: “Zusammenfassende Meldung”, ZM) you report to the Federal Central Tax Office (BZSt), per EU business partner, the taxable base of your intra-Community supplies of a period. Open the module via Reports → EC Sales List in the sidebar (also in the hamburger menu under Reports).

Creating the Report

  1. Choose the year.
  2. Choose the period type: quarter (regular case) or month (from supplies > 50,000 €/quarter).
  3. Choose the period (quarter Q1–Q4 or month).
  4. PDF list creates a printable overview (VAT ID | country | customer | taxable base | type) — for your records or for manual entry.
  5. CSV (ELSTER) creates a file in the official import format that you can upload into the ZM form in the BZSt online portal / ELSTER. You choose the storage location yourself.
  6. ELMA XML creates the BZSt bulk-data XML (see below).

ELMA XML (BZSt Bulk Data)

As an alternative to the ELSTER CSV, the “ELMA XML” button creates a bulk-data file that you upload separately via the BZSt bulk data tool / BOP.

  • Prerequisites: the ELMA account ID (company master → Taxes) and a complete company address including house number (tab Address).
  • Operation: report type (initial report or correction), environment (production or test, from the Taxes tab) plus the options anzeige / widerruf. These two ticks are tied to the report period type: “announce switch to monthly filing” can only be selected for a quarterly report, “revoke monthly filing” only for a monthly report (a disabled tick is cleared automatically).
  • Only igL supplies (transaction type “L”) are covered. You upload the generated file to the BZSt yourself.
Negative rows: If the report contains negative rows (cancellations outweigh the period), a notice appears before the ELMA XML is created (no abort). A CSV with more than 1500 data rows is rejected with an error message instead of producing a file that the ELSTER import would discard. The save dialogs (CSV/ELMA XML) suggest the company export path as the starting folder.
Customer without VAT ID: If an EU customer with igL has no VAT ID, their supply is omitted from the ZM (PDF, CSV and ELMA XML). On creation a non-blocking warning appears listing the affected customers (+ amount), and the case is recorded in the error tracking. The ZM for the remaining customers is still created. Remedy: enter the VAT ID in the customer master.

Data Source & Content

  • The basis are finalized invoices with a VAT class flagged as igL in the selected period (by document date), aggregated per customer by VAT ID.
  • igL detection via the tax key: Whether a line item is an intra-Community supply is determined by the tax key frozen on the document. Renaming or deleting the igL VAT class therefore no longer changes anything about already booked historical documents in the ZM (previously, turnover could silently disappear from the report this way).
  • Cancellation invoices reduce the amounts (negative).
  • Amounts are reported in whole euros (cents dropped); the type of supply is “L” (intra-Community supply).
  • Only customers with a maintained VAT ID appear. Different spellings of the same VAT ID (with/without spaces, dots, hyphens) are combined into one ZM row.
German VAT ID in a report row: If a report row contains a German VAT ID (a misconfiguration in the customer master or the VAT class), it is rejected for PDF, CSV and ELMA XML — with a hint to check the customer master (an igL requires an EU recipient in a different member state).
Scope: Only supplies of goods (type “L”) are covered. Intra-Community other services (§13b, type “S”) and triangular transactions (type “D”) are not included.
Deadline: The ZM is generally due by the 25th day of the following month; if the igL do not exceed 50,000 € per quarter, quarterly filing (by the 25th after quarter end) is allowed. A late report is an administrative offence.

Error Tracking

Error tracking makes fallbacks visible and traceable. The core idea: a fallback is not a harmless default value but a defect in master data maintenance — if the application has to insert a substitute value for lack of data, this can lead to wrong documents, e-invoices or bookings. Data Protection (GDPR)

The program processes personal data of your customers (name, address, contact details, VAT ID etc.). It is therefore subject to the General Data Protection Regulation (GDPR). This chapter describes which statutory data-subject rights the program supports and how to exercise them in practice — and how the program resolves the conflict between the right to erasure and the tax retention obligations.

No legal advice: The following explanations summarise the mechanisms implemented in the program. They do not replace individual legal advice. The operator remains responsible for the data-protection-compliant use.

Legal Basis

The program maps the following legal provisions:

Concept in the Program: Master Data vs. Document Data

The key to resolving the conflict is the separation of customer master and document:

  • A document (quote, order, delivery note, invoice, reminder) internally references the customer master only via a customer number.
  • As soon as a document is finalized or printed, the complete customer record is frozen in the document as a snapshot. Address, salutation, VAT ID etc. are thus preserved exactly as they were at document time (§ 14 UStG).
  • Every output of a document (print, e-invoice, email, access report) always uses this snapshot. The live customer master is only consulted when no snapshot exists (yet).

This allows the customer master to be anonymised in a data-protection-compliant way without finalized documents losing their meaning — an already printed document remains reproducible unchanged.

What “anonymise” means in the master: The personal master fields are irrevocably emptied — salutation, first/last name, company name, address suffix, street, ZIP, city, country, phone, email, notes, VAT ID, letter salutation and Leitweg-ID. The last name is set to “anonymisiert”, the record is removed from the active customer list. The customer number remains as a pseudonym so the document assignment stays intact.

Retention Period

You set the retention period company-wide: Company master → Parameters → Control → “Retention period (years)” (default 10 years).

  • The period runs per customer from the most recent document date across all document types.
  • While the period for a customer's documents has not yet expired, the program prevents final anonymisation/deletion (Art. 17(3)(b) GDPR). Instead of deleting, processing is restricted (Art. 18) — the program points this out on the attempt.
  • If a customer has no documents, there is no retention period — deletion is possible immediately.

Customer-Related Actions

The GDPR functions relating to a single customer live in the customer master: select the customer → button “DSGVO”. A menu with three actions opens:

ActionLegal basisEffect
Access reportArt. 15 + 20Creates a PDF report for the customer (master data + list of all documents with type, number, date) and a machine-readable JSON export. Also works for already anonymised customers (then without personal master data).
Anonymise / deleteArt. 17First freezes the customer data as a snapshot in all not-yet-finalized documents and then empties the personal master fields irrevocably. If the retention period is still open, only the processing is restricted automatically instead.
Restrict processingArt. 18Marks the customer as restricted in processing without deleting data — e.g. upon the customer's objection or during an ongoing review.

Anonymised or restricted customers are indicated in the customer list via a tooltip (hover over the row).

Irrevocable: Anonymising empties the personal master data permanently — there is no restore. Perform it only after deliberate review. The document assignment (customer number) and finalized documents remain unaffected.

Batch Run (Annual Run)

While the customer actions handle a single record, the batch run is a company-wide action — typically once a year. Open it via Reports → GDPR batch run (hamburger menu or sidebar).

  • The program determines all due customers: at least one document, retention period expired, not yet anonymised.
  • They are shown in a table (customer number, name, most recent document date, number of documents) — all pre-selected. Adjust the selection via the check marks or “Toggle all”.
  • After confirmation the selected customers are anonymised in one go.
  • If there are no due customers, the program reports this and ends the run.

Storage & Logs

All GDPR files (access reports and batch-run logs) are stored as PDF and JSON. The storage location follows a convention — no path is stored in the database:

  • Decisive is Company master → Paths → “Directory for GDPR exports”.
  • If the field is empty, {export path}\DSGVO\ is used.
  • Within the directory, files are stored separated by company number.

The batch-run log serves the accountability obligation (Art. 5(2) GDPR) and is deliberately pseudonymous: it only contains the customer number, the number of documents and the most recent document date per anonymised customer plus the executing user — no clear names. This preserves the proof of the performed erasure without storing the erased data again.

User Administration

Everyone who works with the program is a user. In the user administration you define who may sign in and what they may do in which company.

You find the user administration in the menu (hamburger icon) as the red entry User administration. It is reserved for administrators — but the right to it can be granted to individual users.

Signing in

The sign-in dialog always appears when the program starts — including for users with Windows sign-in. The dialog is pre-filled with the currently signed-in Windows user.

  • In the customer master the GDPR report stays possible from level “read”. Anonymise and restrict processing, by contrast, require the level “delete”, because they change customer data permanently.

Test Mode

Test mode lets you test time-dependent features (due dates, reminder levels) by artificially advancing the document date.

Activate

  1. Hamburger menu → Settings
  2. Tick “Test mode” and confirm with OK
  3. A +10 button appears in the sidebar below the document date

How it works

  • Every click on +10 advances the document date by 10 days
  • This lets you jump into the “future” and trigger e.g. higher reminder levels
  • The test mode activation is persistent (stays on after restart)
  • The artificial document date itself is not persistent — on restart it returns to today
Warning: Documents created in test mode are saved with the current document date. Cancel or delete test documents before switching back to production use — or work in a separate test company.

Database & Backup

All data is stored in an SQLite database (app/daten/auftragsabwicklung.db).

Automatic schema updates

On application start the database version is checked and automatically brought to the current state. You do not need to do anything manually.

Creating a backup

A backup is easy — just copy the database file:

copy app\daten\auftragsabwicklung.db app\daten\auftragsabwicklung.db.bak

Or use the export function in the menu (Menu File → Export data).

Encrypted Credentials (key files)

All secret credentials — API keys (Brevo, AI/OpenRouter/Anthropic, address check) as well as SMTP/app/certificate passwords — are not stored in the database, but encrypted in a separate file per company: app\daten\api_keys_{company number}.json. The encryption password is assigned automatically and is never visible.

  • The JSON export (File menu) never contains keys or passwords; after an import the keys may have to be entered again.
  • The key file is part of the backup: back it up together with the database. Without the database it is useless, and without it a restored database is missing all credentials.
  • Status and reset (delete the file → new password + re-enter the keys) under Company → Parameters → Control, row “Key file (API keys)”.

Recommendation

Back up regularly! It is recommended to back up the database regularly — e.g. after every change to important documents. A simple method: copy the database file and the key file(s) (app\daten\api_keys_*.json) into a backup directory with date.

Notes & Frequently Asked Questions

Why does the document number only appear on save?

The number is only assigned on save so unsaved documents do not consume a number. If you create a document and then close it, the counter stays unchanged.

What happens when the VAT rate changes?

Every line item stores the VAT rate at the time of its creation. A change of the rate only affects new line items. Old documents stay correct.

Can I restore deleted documents?

Yes. Since all deletions are “soft delete”, the data stays in the database. You can use the “Restore” function to bring the document back.

Why can I not delete a document?

If the document has live successors (e.g. a quote from which an order has been created), deletion is prevented. You must first delete or restore the successors.

Why does the spell checker not appear?

The check requires Hunspell dictionaries. If none are installed the application still works, but without underlining of errors. See Spell Checker.

Page numbering in PDFs

Page numbering is in the format total - current (e.g. 2 - 1, 2 - 2).

Can I edit multiple documents in parallel?

Yes. You can have several tabs open at once and switch between them. Each tab works with the same data, but every change only takes effect when saved.

What is the creation date?

The creation date is locked on the first print of a document (date + time). After that it stays unchangeable and appears in the document dialog as well as in the PDF header (top right). On a test print no creation date is stored.
